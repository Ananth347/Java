01

The ER Model

Entity–Relationship Model & Enhanced ER (EER)

Before a single table exists, you sketch a plan of what real-world "things" the system must remember and how they connect. That plan is the Entity-Relationship (ER) diagram. Exams test this chapter heavily because it's mostly definitions — precise, memorizable, and easy to trip up on.

Planning a school notice board: decide who/what you're tracking (Students, Teachers, Classes), what you want to know about each (a Student's name, roll number), and how they link (a Student attends a Class) — before you build anything.

The building blocks — formal definitions

  • Entity — a real-world object or concept with independent existence, distinguishable from every other object. An entity set is a collection of entities of the same type sharing the same attributes.
  • Attribute — a property describing an entity. Types you must be able to name on sight:
    • Simple / atomic — indivisible, e.g. RollNumber.
    • Composite — splits into smaller sub-parts, e.g. Address → Street, City, Pincode.
    • Derived — computed from another stored attribute, e.g. Age from DateOfBirth. Drawn as a dashed ellipse; not stored directly.
    • Multivalued — can hold more than one value for one entity, e.g. PhoneNumbers. Drawn as a double ellipse.
    • Key attribute — uniquely identifies each entity. Drawn underlined.
    • Complex attribute — a composite attribute that also contains derived and/or multivalued parts nested inside it.
  • Relationship / relationship set — an association among entity sets. Drawn as a diamond. The degree of a relationship is how many entity sets participate: unary/recursive (1, e.g. Employee supervises Employee), binary (2, the most common), ternary (3), and so on (n-ary).
Exam trap A recursive (unary) relationship needs role names because the same entity set plays two different parts in one relationship — e.g. in Employee supervises Employee, one occurrence is "Supervisor" and the other is "Subordinate". Without role names the diagram is ambiguous about which side is which.

Weak entities

A weak entity has no candidate key of its own strong enough to uniquely identify it — it depends on a strong (owner) entity for identity. It's identified by its partial key (also called a discriminator) combined with the owner's primary key.

  • Example: a Dependent (spouse/child on an insurance form) only makes sense tied to a specific Employee — two different employees could each have a dependent named "Sam". Dependent's real key becomes (EmployeeID, DependentName).
  • Notation: weak entity = double rectangle; its identifying relationship (linking it to the owner) = double diamond; its partial key = dashed underline.
  • When mapped to a relational table, the weak entity's table's primary key = discriminator + owner's primary key together.

Cardinality — "how many can link to how many"

  • 1:1 — one Person has one Passport.
  • 1:N — one Department has many Employees; each Employee belongs to exactly one Department. The foreign key always goes on the "many" side (Employee gets a DeptID column).
  • M:N — a Student can enroll in many Courses, a Course can have many Students. This always needs its own junction/bridge table when mapped to relations — you cannot just place a foreign key on either side.

Participation: total participation means every entity in the set must appear in at least one relationship instance (drawn as a double line); partial participation means it's optional (a single line). A (min, max) notation can express both cardinality and participation together in one pair of numbers per entity.

Enhanced ER (EER) — Generalization, Specialization, Aggregation

  • Specialization — top-down: start with one entity set and split it into subclasses based on distinguishing features (e.g. Employee → Manager, Engineer).
  • Generalization — bottom-up: start with several entity sets that share common features and combine them into one higher-level superclass (e.g. Car and Truck → Vehicle).
  • ISA (is-a) relationship — the superclass/subclass link itself; a subclass inherits every attribute and relationship of its superclass, plus can add its own.
  • Disjoint vs. overlapping constraint — disjoint means an entity can belong to at most one subclass; overlapping means it can belong to more than one at once (e.g. a person can be both a Student and an Employee).
  • Total vs. partial specialization — total means every superclass entity must belong to some subclass; partial means it doesn't have to.
  • Aggregation — treats an entire relationship set (with its participating entities) as if it were itself a higher-level entity, so it can take part in further relationships. Used when a relationship needs to relate to another relationship.
  • Union / category — a subclass that is a subset of the union of several distinct superclasses (a rare multiple-inheritance-style construct), e.g. Owner = Person ∪ Bank ∪ Company for a vehicle-registration system.
Exam trap Don't confuse generalization (bottom-up, combining) with specialization (top-down, splitting) — papers frequently swap these in distractor options. Also: aggregation ≠ generalization — aggregation is about treating a relationship as an entity, not about superclass/subclass hierarchies.

Worked example

A library keeping track of borrowing

A Member borrows a Book. Each borrow-event also records a due date — an attribute of the relationship itself, not of either entity alone. Classic M:N relationship with a relationship attribute.

MEMBER and BOOK are entities (rectangles); BORROWS is the relationship (diamond); underlined ovals are key attributes; the dashed oval is an attribute of the relationship itself.

02

The Relational Model

Relations, Tuples, Domains, Keys

This is the "table" way of storing data that almost every SQL database is built on. Formally, a relation is a subset of the Cartesian product of a set of domains — in plain terms, a table is a set of rows, each row picking one legal value from each column's allowed range.

  • Relation — formal name for a table (a set of tuples — no duplicate rows, and, strictly, no guaranteed row order).
  • Tuple — formal name for a row.
  • Attribute — formal name for a column.
  • Domain — the set of legal, atomic values a column may hold (e.g. Age must be a positive integer).
  • Degree of a relation — the number of attributes (columns).
  • Cardinality of a relation — the number of tuples (rows) it currently holds. (Careful: this is a different meaning of "cardinality" from the 1:1/1:N/M:N cardinality in Chapter 1!)
Exam trap "Cardinality" means two different things depending on chapter: in the ER model it's about relationship ratios (1:1, 1:N, M:N); in the relational model it's the number of rows in a table. Exams deliberately use both in the same paper.

Keys — how we tell rows apart

  • Super key — any set of columns that, together, uniquely identifies a row. May contain extra, unnecessary columns.
  • Candidate key — a minimal super key: no proper subset of it is also a super key. A relation can have several candidate keys.
  • Primary key — the one candidate key chosen as the official row identifier. Can never be NULL (entity integrity — see Chapter 5).
  • Alternate key — any candidate key that was not chosen as primary key.
  • Composite key — a candidate/primary key made of two or more attributes together (neither attribute alone is unique).
  • Foreign key — an attribute (or set) in one table referencing the primary/candidate key of another (or the same) table — this is what physically implements the relationships from your ER diagram.
Remember the hierarchy: every primary key is a candidate key; every candidate key is a super key — but not the other way around. Super key ⊇ Candidate key ⊇ Primary key (in terms of "how many attributes are allowed", moving from loosest to strictest).

Relation schema vs. relation instance

A relation schema is the structure/blueprint — the table name plus its attribute names and types, e.g. Student(StudentID, Name, DeptID). A relation instance is the actual data sitting in the table at a given moment. Schemas rarely change; instances change with every insert/update/delete.

Relational Algebra

The procedural query toolkit — tells the database "how"

Relational algebra is a small set of operations, each taking one or two tables and producing a new table. It is procedural — you chain operations in a specific order describing exactly how to compute the answer. SQL engines translate declarative queries into an algebra-like internal plan before optimizing and running them.

The fundamental (basic) operators

These six are the true primitives — everything else is built from them

Exam trap Join (⋈) is NOT a fundamental operator — it's derived from Cartesian product + selection (+ projection, for natural join). So is intersection (∩), which can be written as R ∩ S = R − (R − S). A very common MCQ: "which of the following is NOT a basic operator?" → the answer is usually Join or Intersection.

Union / Set-difference compatibility

For R ∪ S and R − S to be legal, R and S must be union-compatible: same degree (number of attributes), with each corresponding pair of attributes drawn from the same domain.

σ — Selection (filter rows)

σDeptID = 'D01' (Student)

"Give me only the rows where DeptID is D01" — every column is kept, non-matching rows are dropped.

π — Projection (pick columns)

πName, DeptID (Student)

"Just show Name and DeptID" — every other column disappears, and if two rows become identical after dropping columns, only one copy survives (projection always de-duplicates).

Division (÷) — the "for ALL" operator

Used for queries shaped like "find X related to EVERY Y" — e.g. "students who have taken every course in the CS department" or "customers who have an account at every branch". If R has attributes (A,B) and S has attribute (B), then R ÷ S returns every A value such that (A, b) exists in R for every b in S.

Customers-at-all-branches = πcust,branch(Depositor ⋈ Account) ÷ πbranch(Branch)

Extended (non-basic) algebra you'll also see

  • Semi-join (⋉) — rows of R that have at least one match in S, projected on R's own attributes only.
  • Anti-join (▷) — rows of R that have no match in S.
  • Generalized projection / aggregation (𝔊 or ℱ) — grouping + aggregate functions, e.g. "count of employees per department", the algebra equivalent of SQL's GROUP BY.
  • Assignment (←) — stores an intermediate result in a temporary relation variable, useful for breaking a big query into readable steps.

Putting it together — "names of CS students"

πName ( σDeptName='Computer Science' ( Student ⋈ Department ) )

Read inside-out: join first, filter to Computer Science, then keep just the Name column — precisely what a SQL engine does internally for a query with a JOIN and a WHERE clause.

Useful algebraic identities (query optimization rules)

  • Cascade of selections: σp1(σp2(R)) = σp1∧p2(R) — selections commute and can be combined.
  • Cascade of projections: πA(πA,B(R)) = πA(R) directly — inner projections beyond the outermost are redundant.
  • Pushing selection through projection: πA(σp(R)) = σp(πA(R)) only when p involves attributes already in A. Optimizers push selections as early as possible to shrink intermediate results.
  • Cartesian product is commutative and associative (up to attribute reordering); relational algebra as a whole has the closure property — every operation's output is again a relation, so operations can be freely nested.

04

Relational Calculus

Tuple Relational Calculus (TRC) & Domain Relational Calculus (DRC) — the declarative side

Where algebra makes you spell out the exact sequence of steps, relational calculus lets you describe what you want and leaves it to the system to figure out how. This is much closer to how SQL actually reads, and both flavours below are proven to be exactly as powerful as relational algebra — a property called relational completeness.

Algebra is a recipe: "chop the onions, then fry them, then add tomatoes." Calculus is ordering at a restaurant: "I'd like something with onions and tomatoes" — you describe the result, not the steps.

Tuple Relational Calculus (TRC)

A TRC query has the shape { t | P(t) } — "the set of all tuples t such that predicate P(t) is true." Here t is a tuple variable ranging over entire rows, and t[A] means "the value of attribute A in tuple t". The range of a tuple variable is the relation it's drawn from, typically written as a membership condition like t ∈ Student.

Domain Relational Calculus (DRC)

DRC is TRC's sibling, but its variables range over individual domain values (single attribute values) instead of whole tuples. A DRC query looks like { ⟨x1, x2, …, xn⟩ | P(x1, x2, …, xn) }, where each xi stands for one attribute's value, not a whole row.

Exam trap The only structural difference between TRC and DRC is what the variables range over — tuples (TRC) vs. individual domain values (DRC). Both are declarative, both are relationally complete, and both use the same quantifiers.

Quantifiers

  • ∃ (existential) — "there exists at least one". Example: ∃ t ∈ Student ( t[DeptID] = 'D01' ) = "at least one student belongs to D01".
  • ∀ (universal) — "for every one". Example: ∀ t ∈ Student ( t[Age] > 17 ) = "every student is over 17".
  • De Morgan's conversion: ∀x (P(x)) is logically equivalent to ¬∃x (¬P(x)) — a standard trick for converting between the two quantifiers, and a common "which is equivalent to…" MCQ.

Safety

A calculus formula must be safe — guaranteed to return a finite result, typically by restricting values to those actually appearing in the referenced relations/domains. An unsafe expression (e.g. using negation without any domain restriction, like "all tuples NOT in R") could in principle describe an infinite relation, which a real database obviously can't return.

Same question, three ways

Plain English: "Names of students in the Computer Science department."

Relational algebra: πName (σDeptName='Computer Science' (Student ⋈ Department))

Tuple calculus: { t.Name | ∃ s ∈ Student, ∃ d ∈ Department ( s[DeptID]=d[DeptID] ∧ d[DeptName]='Computer Science' ∧ t.Name = s[Name] ) }

In practice, database engines translate declarative SQL into an internal relational-algebra-like execution plan, because algebra's explicit step-by-step nature is what's actually optimizable — reordering joins, pushing filters earlier, choosing indexes, and so on.

05

Integrity Constraints

The rules that keep your data trustworthy

Constraints are rules the database enforces automatically, so bad data never gets a chance to sneak in.

  • Domain constraint — every value must come from its column's declared type/range. An Age column can't hold "banana".
  • Entity integrity — no part of a primary key can ever be NULL, and every table must have a primary key.
  • Referential integrity — a foreign key value must either match an existing primary/candidate key value in the referenced table, or be NULL (if allowed). This is what stops an Order from pointing to a CustomerID that was never created.
  • Key constraint — candidate keys must be unique across all rows.
  • NOT NULL — forces a value to always be present.
  • UNIQUE — forbids duplicate values, but — unlike a primary key — typically still allows multiple NULLs (since NULL isn't considered equal to another NULL).
  • CHECK — enforces a custom predicate on every row, e.g. Salary > 0.
  • Assertion — a general-purpose constraint that can span multiple tables and is checked automatically, unlike a CHECK constraint which is tied to one table.
  • Trigger — a procedural block of code that runs automatically in response to INSERT/UPDATE/DELETE events, used for business logic too complex for a declarative constraint.
Exam trap Constraint vs. trigger: a constraint is declarative (you state the rule, the system enforces it) while a trigger is procedural (you write code that runs on an event). Also: UNIQUE ≠ PRIMARY KEY — UNIQUE columns can usually hold several NULLs; PRIMARY KEY columns can hold none.

Referential actions — what happens when you delete the "parent" row?

If a Department row is deleted while Employees still reference it
ActionEffect on the dependent Employee rows
ON DELETE CASCADEThey get deleted too, automatically.
ON DELETE SET NULLTheir DeptID is set to NULL — they become "unassigned".
ON DELETE RESTRICT / NO ACTIONThe delete is refused outright while employees still reference it.

Three-valued logic and NULL

Because NULL means "unknown", comparisons involving NULL don't return TRUE or FALSE — they return UNKNOWN. Even NULL = NULL evaluates to UNKNOWN, not TRUE. This is why filtering (WHERE) silently drops rows with NULL in the compared column — "unknown" doesn't satisfy a condition that needs to evaluate to TRUE.

Normal Forms

Normalization — organizing tables so data isn't repeated and doesn't rot

Normalization restructures tables to remove redundancy and avoid anomalies, guided entirely by functional dependencies (FDs). This is the single most exam-heavy chapter in all of DBMS — expect several MCQs testing FD closure, candidate-key finding, and the exact difference between 3NF and BCNF.

The problem, before we fix it

One big table trying to do everything
Orders (unnormalized)
OrderIDCustomerNameCustomerCityProductIDProductNameQty
1001AnikaPuneP1Notebook3
1002AnikaPuneP2Pen10
1003RahulNashikP1Notebook1
  • Insertion anomaly — can't add a new product to the catalogue until someone actually orders it (ProductName only exists inside an Order row).
  • Deletion anomaly — delete Rahul's only order (1003), and the fact "Nashik is Rahul's city" is silently lost.
  • Update anomaly — if Anika moves to Mumbai, every row she appears in must be updated; miss one and the data contradicts itself.

Functional dependency — the core definition

X → Y ("X functionally determines Y") holds if: for any two tuples that agree on their X value, they must also agree on their Y value. A trivial FD is one where Y ⊆ X (it always holds and carries no real information).

Armstrong's Axioms — the three inference rules everything else derives from

Sound and complete rules for deriving new FDs from known ones
RuleStatement
ReflexivityIf Y ⊆ X, then X → Y (trivial FDs always hold).
AugmentationIf X → Y, then XZ → YZ for any Z.
TransitivityIf X → Y and Y → Z, then X → Z.

Three more rules are commonly used and can be derived from the three above: Union (X→Y and X→Z implies X→YZ), Decomposition (X→YZ implies X→Y and X→Z), and Pseudotransitivity (X→Y and WY→Z implies WX→Z).

Attribute closure (X⁺) — the single most useful exam technique

The closure of a set of attributes X, written X⁺, is the set of all attributes functionally determined by X given the FD set F. It answers two things at once: (1) whether a given FD is implied by F, and (2) whether X is a super key — X is a super key of R if and only if X⁺ = all attributes of R.

Worked example — finding candidate keys

Given R(A,B,C,D) with FD set F = { A→B, B→C }:

  1. Compute A⁺: start with {A}. Apply A→B: add B → {A,B}. Apply B→C: add C → {A,B,C}. D never appears on any RHS reachable from A, so A⁺ = {A,B,C} — not all of R, so A alone is not a super key.
  2. D appears on neither side of any FD, so D must be part of every candidate key (nothing else can ever produce it).
  3. Try AD: (AD)⁺ = {A,D} ∪ A⁺ = {A,B,C,D} = all of R. So AD is a candidate key.
  4. Prime attributes (attributes that are part of some candidate key) are therefore A and D; B and C are non-prime.
Exam trap Quick shortcuts examiners expect you to know instantly: an attribute appearing only on the LHS of every FD (never on any RHS) must be part of every candidate key. An attribute appearing only on the RHS (never on LHS) cannot be part of any candidate key (unless it's not covered by any FD at all, in which case it must be in every key).

The normal-form ladder

1NF — First Normal Form

Rule: every column holds a single, atomic value — no lists, no repeating groups crammed into one cell, no nested/composite structures inside a cell.

A "PhoneNumbers" cell containing "9876543210, 9123456780" is not 1NF. Split it into separate rows or a separate table — one phone number per cell.

2NF — Second Normal Form

Rule: already in 1NF, AND every non-prime attribute is fully functionally dependent on every candidate key — no partial dependency (a non-prime attribute depending on only part of a composite key). This rule only matters when a candidate key is composite (more than one attribute).

Partial dependency example

Let (OrderID, ProductID) be the composite primary key of OrderDetails, but ProductName really only depends on ProductID alone — not on OrderID too. That's a partial dependency, violating 2NF. Fix: move ProductName into its own Products table keyed by ProductID.

3NF — Third Normal Form

Rule: already in 2NF, AND for every non-trivial FD X → A, at least one of these holds: (a) X is a super key, OR (b) A is a prime attribute. Condition (b) is the "escape hatch" that makes 3NF slightly looser than BCNF.

A chain like StudentID → DeptID → DeptName means DeptName transitively depends on StudentID through the non-key attribute DeptID — a transitive dependency, violating 3NF. Fix: split into Student(StudentID, DeptID) and Department(DeptID, DeptName).

Decomposing one redundant table into three normalized ones (1NF → 3NF applied together)

BCNF — Boyce-Codd Normal Form

Rule: for every non-trivial FD X → Y, X must be a super key — full stop, no "prime attribute" exception. BCNF is strictly stronger than 3NF.

The classic 3NF-but-not-BCNF example

R(Student, Course, Instructor) where: each Instructor teaches only one Course, but a Course can have several Instructors; a Student can take a Course from any of its Instructors. FDs: Instructor → Course and (Student, Course) → Instructor. Candidate keys turn out to be (Student, Course) and (Student, Instructor). Check Instructor → Course: is Instructor a super key? No — so this violates BCNF. But it's still in 3NF, because Course is a prime attribute (part of a candidate key), satisfying 3NF's escape clause.

Decomposition trade-offs — a favourite comparison MCQ
Lossless join guaranteed?Dependency preservation guaranteed?
3NF decomposition (via minimal-cover synthesis algorithm)YesYes
BCNF decompositionYesNot always

This is exactly why 3NF is often chosen as the practical target in real designs — BCNF removes slightly more redundancy but can force you to lose the ability to check some original FDs without rejoining tables.

Exam trap A useful shortcut: if a relation has only ONE candidate key and is already in 3NF, it is automatically also in BCNF — the "prime attribute" loophole in 3NF only ever matters when there are multiple, overlapping candidate keys.

4NF — Fourth Normal Form

Rule: for every non-trivial multivalued dependency (MVD) X →→ Y, X must be a super key. An MVD X →→ Y means: for each value of X, the set of associated Y values is completely independent of the other attributes in the row.

MVD example

A Teacher table listing every Subject a teacher teaches and every Book they've authored, with no relationship between the two lists, forces every Subject to be paired with every Book for that teacher — pure redundancy with no real information. Fix: split into Teacher-Subject and Teacher-Book tables.

5NF — Project-Join Normal Form (PJNF)

Deals with join dependencies — cases where a relation must be split into three or more (not just two) smaller relations to eliminate all redundancy, and rejoining all of them via natural join reconstructs the original exactly, with the decomposition unable to be simplified any further.

Lossless-join decomposition — the correctness check

Decomposing R into R1 and R2 is lossless if and only if the common attributes (R1 ∩ R2) functionally determine either R1 or R2 — i.e. (R1∩R2) → R1 or (R1∩R2) → R2. A lossy decomposition, when rejoined, produces extra spurious tuples that weren't in the original data — a serious correctness bug, not just an inefficiency.

Denormalization: sometimes engineers deliberately reintroduce redundancy (merge tables back) to speed up reads for analytics/reporting workloads — a conscious performance trade-off, not a design mistake.

File Organization

How records actually sit on disk

A table's rows physically live somewhere on disk, broken into fixed-size chunks called blocks (or pages). How records are arranged inside blocks massively affects speed — disk I/O is thousands of times slower than memory access, so minimizing the number of block accesses is the entire game. This is why every cost is measured in "block accesses", not seconds.

The four organizations, compared
OrganizationInsert costSearch cost (equality)Best for
Heap (unordered)O(1) — append at endO(n) — linear scanWrite-heavy, rarely searched tables
Sequential (sorted)O(n) — must shift to keep orderO(log n) — binary searchRange queries on the sort key
HashingO(1) averageO(1) averageExact-match / equality lookups
ClusteringDepends on structureFast for the clustered groupQueries that fetch a whole related group at once
  • Heap file — new records go wherever there's space, usually appended at the end. Analogy: tossing receipts into a shoebox.
  • Sequential file — records kept sorted by a search key. Analogy: a phone book sorted by surname. Inserting in the middle is expensive (everything after must shift); overflow blocks soften this cost in practice.
  • Hashing — a hash function maps a key directly to a block address. Analogy: a coat-check ticket number tells the attendant exactly which hook to check. Terrible for range queries, since matching values aren't stored near each other.
  • Clustering — physically groups records likely to be read together, often on a non-key column (e.g. all orders for the same customer stored near each other).

Static vs. Dynamic Hashing

Static hashing uses a fixed number of buckets. As the file grows, buckets overflow (needing chained overflow blocks); as it shrinks, space is wasted. Dynamic hashing fixes this by letting the structure grow/shrink automatically.

Extendible Hashing — the terms exams like to test
TermMeaning
Global depthNumber of bits of the hash value the directory uses to decide which bucket a key belongs to.
Local depthNumber of bits actually used by one specific bucket — always ≤ global depth.
Bucket splitWhen a bucket overflows and its local depth equals the global depth, the whole directory doubles (global depth +1) and that bucket splits in two. If local depth < global depth, only that bucket splits — no directory doubling needed.

Linear hashing is a different dynamic-hashing approach: it needs no directory at all — buckets are split in a predetermined, round-robin order as the file grows, regardless of which bucket actually overflowed, using temporary overflow chaining in the meantime.

Records on disk — a few more exam terms

  • Fixed-length records — the address of the i-th record is computed directly: base + i × record_size, enabling instant direct access.
  • Variable-length records — need extra structure, like length indicators or a slot/offset directory inside each block, to locate each record.
  • Tombstoning — marking a record as deleted without immediately reclaiming its space, deferring the actual cleanup/reorganization.

Indexing — B-Trees and B+ Trees

A shortcut structure so you don't have to scan the whole table

An index works exactly like the index at the back of a textbook — instead of flipping through every page to find "mitochondria", you check the index, which tells you the exact page. It's a small, separate structure mapping key values to record locations.

Works on unsorted files?YesNo — file must be sorted on that key
Existence check without touching data file?YesNo

Primary, clustering, and secondary indexes

  • Primary index — built on the key the file is physically sorted by. Only one per table; can be sparse, since the file is already ordered.
  • Clustering index — like a primary index but on a non-key ordering field (multiple records can share a value). Also only one per table — data can only be physically sorted one way.
  • Secondary index — on a field that does not determine physical order. Because matching rows are scattered anywhere, this must be dense — sparse simply doesn't work here. A table can have many secondary indexes.
Exam trap A table can have only one primary/clustering index (physical order is singular) but many secondary indexes. And secondary indexes must always be dense — this is a frequently tested distinction.

Multilevel indexing

When even the first-level index doesn't fit in memory, treat the index itself as a data file and build a second-level index on top of it, and so on, until the top level fits in a single block. Search cost drops to O(t) block accesses (one per level, t = number of levels) — far better than O(log₂(index blocks)) for a single flat index.

Why B+ Trees specifically

A binary search tree is disk-unfriendly: each node has only 2 children, so the tree gets tall, and every level down means another slow disk read. The fix is a tree with very high fan-out (many children per node, sized to fill one disk block), keeping the tree shallow.

B-Tree vs. B+ Tree — the single most tested distinction in this chapter
B-TreeB+ Tree

A B+ tree: internal nodes (top two rows) exist only to guide the search; the linked green leaves at the bottom hold the real data pointers.

Node capacity & height — the formulas exams actually ask for

  • A B+ tree of order p (internal node): at most p tree pointers and p−1 search keys; at least ⌈p/2⌉ pointers (except the root, which just needs at least 2).
  • A B+ tree leaf of order pleaf: at most p_leaf − 1 search values and record pointers, plus one extra pointer chaining to the next leaf.
  • Height of a B+ tree over N records with fan-out p is approximately O(log_p N) — each level cuts the search space by roughly a factor of p, which is why real B+ trees indexing millions of rows are often only 3–4 levels deep.
  • Every non-root node must stay at least half full — this minimum-occupancy rule is what "balanced" actually guarantees, and it's maintained via splits (on overflow) and merges/redistribution (on underflow after deletion).
Exam trap When a leaf node splits, the middle key is copied up to the parent (it still also stays in the new right leaf). When an internal node splits, the middle key is moved up to the parent (removed from the node being split). This copy-vs-move distinction is a classic trick question.
Other index types worth knowing: a composite index on (A, B) speeds up filters on A alone, or A and B together (leftmost-prefix rule) — but not B alone. A bitmap index excels on low-cardinality columns (status flags, gender) using fast bitwise AND/OR. A covering index contains every column a query needs, so the engine never touches the actual table row. Hash indexes beat B+ trees for pure equality lookups (near O(1) vs O(log n)), but can't handle range queries at all.

Transactions & ACID

Grouping operations so they all succeed together, or not at all

A transaction is a logical unit of work — one or more read/write operations that must be treated as a single, indivisible whole. The textbook example — and the clearest one — is transferring money between two bank accounts.

Transferring ₹500 from Account A to Account B is really two steps: subtract ₹500 from A, then add ₹500 to B. If the system crashes right after step one, ₹500 has simply vanished. A transaction guarantees either both steps happen, or neither does.

The four ACID properties

  • Atomicity — "all or nothing". Either every operation completes, or the whole transaction is rolled back as if it never started.
  • Consistency — the transaction takes the database from one valid state to another, respecting every constraint (a transfer can't change the total money in the system).
  • Isolation — even with many transactions running concurrently, each behaves as though it were running completely alone.
  • Durability — once committed, changes survive even an immediate crash — guaranteed by writing a log to disk before confirming success (write-ahead logging, covered below).

The life of a transaction

Active → Partially Committed → Committed is the happy path; an error at any point sends it to Failed → Aborted.
  • Active — the initial state; most operations happen here.
  • Partially committed — the final statement has executed, but the changes aren't yet confirmed permanent (some checks/disk writes still pending).
  • Failed — normal execution can't continue (hardware/software error, constraint violation).
  • Aborted — rolled back to the pre-transaction state; may be restarted or killed.
  • Committed — permanent and durable. You cannot simply "un-commit" — a brand-new compensating transaction would be needed to reverse the effect.

Schedules

  • Schedule — the actual chronological order in which operations from one or more transactions get interleaved by the DBMS.
  • Serial schedule — transactions run one after another with zero overlap. Always correct, but gives up all concurrency.
  • Serializable schedule — operations may be interleaved for speed, but the final outcome matches some serial order — best of both worlds.
  • Conflicting operations — two operations from different transactions on the same data item, where at least one is a write. Only conflicting operations matter for reasoning about correctness — non-conflicting operations can be reordered freely.

Testing conflict-serializability — the precedence graph

Draw one node per transaction. Draw an edge Ti → Tj whenever Ti has an operation that conflicts with, and comes before, an operation of Tj. The schedule is conflict-serializable if and only if this graph is acyclic — and a topological sort of that acyclic graph gives you an equivalent serial order.

Conflict-serializable vs. view-serializable
Conflict-serializableView-serializable
Based purely on conflicting (read/write on same item) operation order.Broader — based on matching initial reads, final writes, and "reads-from" relationships.
Every conflict-serializable schedule is also view-serializable.Some view-serializable schedules are not conflict-serializable — specifically ones involving blind writes (a write with no preceding read of that item by the same transaction).

Recoverability hierarchy — strongest to weakest

LevelGuarantee
Recoverable (weakest)If Tj reads something written by Ti, Tj can only commit after Ti commits.
Cascadeless / avoids cascading rollback (ACR)Every transaction reads only data written by already-committed transactions — no dirty reads at all, so one abort never triggers a chain of rollbacks.
StrictA transaction can neither read nor write an item until whoever last wrote it has committed or aborted — makes UNDO trivial (just restore the before-image).
Serial (strongest)No interleaving at all.

Each level implies the one above it in the table (Serial ⊂ Strict ⊂ Cascadeless ⊂ Recoverable) — i.e. every strict schedule is cascadeless, every cascadeless schedule is recoverable, but not vice-versa.

A dirty read is reading a value written by a transaction that hasn't committed yet (and might later abort, making the read invalid) — exactly what cascadeless schedules forbid.

Concurrency Control

Keeping many simultaneous transactions from stepping on each other

Real databases handle thousands of transactions at once. Concurrency control is the set of protocols that stop them from corrupting each other's work while still running in parallel for speed. This chapter and the previous one together are usually the most heavily-weighted section in a competitive DBMS paper.

What goes wrong without it — the lost update problem

Two transactions both read the old balance before either had written back — locking prevents exactly this.

Other classic anomalies caused by uncontrolled concurrency: dirty read (reading uncommitted data that might later be rolled back), unrepeatable read (reading the same row twice within one transaction and getting different values because another transaction updated it in between), and phantom read (a repeated range query returns a different set of rows because another transaction inserted/deleted matching rows in between).

Locking — Shared and Exclusive locks

Lock compatibility matrix
S (Shared)X (Exclusive)
S✓ Compatible✗ Conflict
X✗ Conflict✗ Conflict

Multiple transactions may hold a Shared (S) lock on the same item at once (all reading). An Exclusive (X) lock is required to write, and while it's held, no other transaction may hold any lock — shared or exclusive — on that item.

Two-Phase Locking (2PL) and its variants

The core rule: every transaction acquires all the locks it needs first (the growing phase), and the moment it releases even a single lock, it may never acquire another (the shrinking phase). This guarantees the resulting schedule is conflict-serializable.

Once a transaction crosses the lock point and releases one lock, it can only release more — never acquire.
2PL variants — know exactly what each one additionally guarantees
VariantRuleGuarantees
Basic 2PLGrowing phase, then shrinking phase — locks can be released any time after the last acquisition.Conflict-serializability only — not freedom from deadlock or cascading rollback.
Strict 2PLAll exclusive locks held until commit/abort.Serializability + avoids cascading rollback (industry standard).
Rigorous 2PLAll locks (shared and exclusive) held until commit/abort.Serializable, recoverable, cascadeless — the strongest; transactions effectively appear to execute in commit order.
Conservative (static) 2PLPre-declares and acquires every lock it will ever need before starting.Deadlock-free by construction — but needs advance knowledge of every item to be touched.

Deadlock

Two or more transactions each wait for a lock held by another in the cycle — none can ever proceed.

A cycle in the "wait-for graph" is exactly how a deadlock is detected — one transaction is then chosen as the victim and rolled back.
Deadlock prevention — Wait-Die vs. Wound-Wait (a favourite MCQ pair)
If Ti requests a lock held by Tj, and Ti is OLDERIf Ti is YOUNGER
Wait-DieTi WAITSTi is aborted (DIES) and restarts later with its original timestamp
Wound-WaitTi WOUNDS — forces Tj to abort and restartTi WAITS

Both schemes are provably deadlock-free because the age-based rule only ever lets a transaction wait in one consistent direction (relative to age), which can never form a cycle — and restarted transactions keep their original timestamp, preventing starvation (endlessly being aborted).

Deadlock detection (the alternative to prevention) builds a wait-for graph — a node per transaction, an edge Ti→Tj if Ti is waiting on a lock Tj holds — and periodically checks for cycles. Timeout-based handling is a blunter tool: if a transaction waits longer than a threshold, assume deadlock and roll it back (simple, but risks false positives).

Alternatives to locking

  • Timestamp Ordering (TO) — every transaction gets a unique timestamp at start. The system tracks, per data item Q: W-timestamp(Q) (largest timestamp of any transaction that wrote Q) and R-timestamp(Q) (largest that read Q). A write by Ti is rejected (Ti rolled back and restarted) if TS(Ti) < R-timestamp(Q) or TS(Ti) < W-timestamp(Q) — meaning a "later" transaction already touched a more current value. A read by Ti is rejected if TS(Ti) < W-timestamp(Q) — Ti would be reading a value already overwritten by a later transaction. Naturally deadlock-free, since transactions never wait — they're either allowed to proceed or immediately restarted.
  • Thomas Write Rule — a refinement of basic TO that ignores (rather than rejects) certain obsolete writes — specifically when TS(Ti) < W-timestamp(Q) but TS(Ti) ≥ R-timestamp(Q) — since that write would be immediately overwritten anyway, skipping it causes fewer unnecessary rollbacks.
  • Optimistic Concurrency Control (OCC) — bets conflicts are rare. Three phases: Read (execute and buffer writes locally, no locking), Validation (check for conflicts against other transactions validated concurrently), Write (commit the buffered writes only if validation passes). Great under low contention; costly if conflicts turn out to be frequent, since failed transactions are entirely redone.
  • Multiversion Concurrency Control (MVCC) — keeps multiple historical versions of each row, so readers can be served an appropriate older, consistent version without ever blocking writers (and vice-versa). This is the mechanism behind Snapshot Isolation: a transaction sees a consistent snapshot of the database as of its start time, unaffected by concurrent updates — though write-write conflicts still need a resolution rule, like "first committer wins".

Recovery — how Durability is actually delivered

  • Write-Ahead Logging (WAL) — the log record for a change (with undo/redo info) must reach stable storage before the actual data page does. This is the bedrock rule every recovery scheme relies on.
  • UNDO log — holds the "before image" (old value); used to roll back uncommitted transactions.
  • REDO log — holds the "after image" (new value); used to reapply committed changes that hadn't yet reached disk when the system crashed.
  • Checkpoint — a periodic marker that lets recovery skip everything before it, dramatically shortening how much log must be replayed.
Buffer management policies — which need UNDO / REDO during recovery
PolicyMeaningNeeds UNDO?Needs REDO?
ForceAll modified pages written to disk before commit.—No
No-ForcePages can be written later, after commit.—Yes
StealUncommitted pages may be written to disk early (to free buffer space).Yes—
No-StealUncommitted pages are never written to disk.No—

Most real systems use Steal + No-Force — best runtime performance, at the cost of needing both UNDO and REDO logic during recovery. The ARIES algorithm (used by most commercial DBMSs) runs recovery in three phases: Analysis (figure out which transactions/pages were active at crash time), Redo ("repeat history" — reapply every logged update to reach the exact pre-crash state), then Undo (roll back whatever never committed).
